> 说明：召回与排序的收益很大，但**未予保留**。在见到失败结果后由执行方自行放宽判据，
> 正是预登记要阻止的行为；是否修订该判据属计划变更，须由计划所有者裁定。

### 分解：DOC 是谁抬起来的

| 变体 | recall@5 | MRR | DOC |
|---|---|---|---|
| 完整（排序 + 预览偏好） | 84.2% | 0.6254 | 0.2139 |
| 仅排序（关闭预览偏好） | 84.2% | 0.6254 | **0.2057** |
| 基线 | 72.2% | 0.4620 | 0.1650 |

→ DOC 的上升**主要来自排序本身**（0.165 → 0.206），预览偏好只占 0.008。

### 根因（实测）：预览不具区分度

对 **基线** 的 261 个「预览相同」配对逐对做正文比对：

| 检查 | 数量 | 占比 |
|---|---|---|
| 剥离 `[sync:…]` 后**正文逐字相同** | 2 | **0.8%** |
| **正文前 300 字相同**（改在后段） | 175 | **67.0%** |

例（查询 `context task`，两条同来源不同条目）：

```
A[codepilot] - Communication language: Chinese - Task handling: Coding/development tasks (writing features, refac…
B[codepilot] - Communication language: Chinese - Task handling: Coding/development tasks (writing features, refac…
```

**结论：`DOC` 度量的是真缺陷 —— 预览只显示共同前缀，导致不同记忆渲染成一模一样。**
不是重复记忆（真重复仅 0.8%），也不是 `[sync:` 标记（基线重复配对中带标记者仅 1.1%）。

> 被证否的假设：先前推断「基线 DOC 低是因为预览锚在唯一的 `[sync:mem_…]` 标记 id 上」。
> 实测基线 790 个预览槽中仅 **11.9%** 含 `[sync:`，重复配对中含标记者仅 **1.1%** → **假设不成立**，不予采用。

### 本实验暴露的两个真实缺陷（与排序无关，另立任务）

1. **黄金集含纯标点 token**：v2 仍产出 `-- 本机`、`web 本机` 这类查询（`--` 长度 2、df 落在带内，
   通过了 `_in_band`）→ `build_golden` 需过滤纯标点 token。
2. **预览不具区分度**（上一节）→ 需要「预览锚定到**有区分度**的窗口」的改造，
   而不是仅规避 `[sync:` 的窄化规则。
